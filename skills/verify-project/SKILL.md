# 项目正确性检查（verify-project）

## 与 preflight-check 的分工

两个都叫「检查」，但拦的东西完全不重叠，别混用：

| | preflight-check | **verify-project（本 Skill）** |
|---|---|---|
| 拦什么 | **发布环节**漏了什么 | **代码与数据之间的契约**还成不成立 |
| 典型症状 | 线上 404、图裂、SW 静默失效 | 页面白屏但不报错、云函数 500 看不出原因、测试全绿但只跑了 3 条 |
| 什么时候变坏 | 每次发布时 | 每次改字段 / 改方法 / 改测试时 |
| 修一次能好吗 | 能（重新发布就好） | 不能，得回头找是哪次改动破坏了契约 |

**判断用哪个**：症状是「线上不对」→ preflight；症状是「代码不对」→ 本 Skill。

## 怎么跑

```bash
python verify_project.py
```

退出码 `0` = 全通过，`1` = 有失败项。**提交之前必跑。**

本项目提交前的标准顺序：

```bash
python verify_project.py     # 1. 契约检查
python preflight.py          # 2. 发布检查（要发布时才跑）
```

## 24 项检查，每项都来自真实踩过的坑

脚本输出 FAIL 时会**额外打印一行「为什么查这条」**——
这是刻意设计的：一条没有出处的规则，后人会当成冗余删掉，
而这些规则每一条背后都是一个真花过时间的 bug。

### A · 数据契约（6 项）

| 检查项 | 拦什么 |
| --- | --- |
| **A1** SQL 方言兼容（8 类禁用写法） | `TINYINT`（PostgreSQL 没有）、`DATETIME`（时区被转一次）、`BOOLEAN`、列名 `date`（是关键字）、三种 upsert 方言 |
| **A2** 三张表齐全 | 少建一张 → 前端取数直接 404，控制台看不出是「表没建」 |
| **A3** seed 幂等用 DELETE+INSERT | upsert 三家方言各一套写法，没有一种能同时跑三家 |
| **A4** 真实数据 id 不带 `seed-` 前缀 | seed.sql 用 `DELETE ... WHERE id LIKE 'seed-%'` 做幂等，真实数据蹭上这个前缀就被清空，**且无任何提示** |
| **A5** 前后端字段映射双向对齐 + **写入端键名校验** | `createdAt` ↔ `created_at` 只改一边 → 字段静默变 NULL |
| **A6** 时刻列 ISO UTC / 日历列 `CHAR(10)` / 0-1 用 `SMALLINT` | DATETIME 显示差几小时且不报错；`yearly` 存 boolean 在 PG 和 MySQL 行为不同 |

### B · 云函数契约（9 项）—— 部署后才会暴露的那类

| 检查项 | 拦什么 |
| --- | --- |
| **B1** `errors-human` 双路径 require（先 `./` 后 `../`） | 部署包解压成独立根目录，父目录不存在。只写 `../` 的话**部署不报错，一调用就 500**，日志里看不出是路径问题 |
| **B2** 用内置 `https`，不用全局 `fetch` | 运行时可能是 Node 16，那时没有全局 fetch → ReferenceError。**本地 node 版本高，能跑，测不出来** |
| **B3** 环境变量双名兼容 | 官方文档两个拼法都出现过（node-sdk 写 `APIKEY`，AI-Toolkit 写 `API_KEY`）。只读一个 → 另一个拼法静默读不到，报 `CONFIG_MISSING` |
| **B4** 跨域白名单不回退 `*` | 退回 `*` 等于任何网站都能读你的库。另：`localhost` 和 `127.0.0.1` 是**两个不同的源**，只配 localhost 会静默退回本地数据 |
| **B5** 写方法齐全 | 控制台要逐个勾 GET/POST/PATCH/DELETE，漏勾前端调了会 404，**但代码里明明写着** |
| **B6** 走 PostgREST 网关，不走内网直连 | 体验版下内网地址要开「内网互联」、外网直连开关也开不了，两条直连路都不通 |
| **B7** 删除/单查找不到行返回 404 | 200 空结果 = 谎报成功。踩过：点删除 UI 显示已删，刷新又回来了，看不出是后端没删 |
| **B8** 重复提交返回 409（id 当幂等键） | 演示工具把 id 写死，第二次点必然冲突。踩过：POST 截图工具只能截一次 |
| **B9** 服务端密钥不进前端 | API Key 被网关解成 `service_role`，绕过所有行级安全策略。进前端 = 公网可读 = 别人能读写你的库 |

### C · 测试有效性（4 项）—— 专门拦「假绿」

| 检查项 | 拦什么 |
| --- | --- |
| **C1** 测试文件里没有顶层 `return` | Node 模块顶层 `return` 立刻结束模块，**退出码还是 0**。踩过：以为跑了 75 条，实际只跑了 3 条，一片绿 |
| **C2** 全部测试退出码 0 且真的跑出条数 | 退出码 0 不代表跑完了 —— 顶层 return、异常吞掉都能骗过 CI |
| **C3** 没有「只跑了几条」的可疑文件 | 条数突然变少通常是断言被改废了或桩没跟上，而不是「测试变简单了」 |
| **C4** 手写桩覆盖源码实际调用的方法 | 桩按错误假设写，就给错误代码盖章。踩过：加纪念日后 `syncJobs.annivRemove` 没进桩，测试崩了才知道 |

### D · 密钥边界（2 项）

| 检查项 | 拦什么 |
| --- | --- |
| **D1** 工作区（除 `.git`/`.deploy`）无真实密钥 | 一旦 commit 进历史，删文件也还在，只能改密钥 |
| **D2** Git **全历史**无真实密钥 | 历史里的密钥等于永久泄露，删文件 / rebase 都清不掉 |

### E · 前后端契约一致（3 项）

| 检查项 | 拦什么 |
| --- | --- |
| **E1** 前端调用的每个 API 路径都有云函数 | 前端加了接口但云函数没部署 → 404，页面退回本地数据，很容易被当成「后端还没做」而不是「部署漏了」 |
| **E2** 没有孤儿云函数（建了但前端从不调） | 孤儿函数通常意味着「这功能还没接完」，留着容易让人以为已经做完 |
| **E3** 前端 env ID 与云函数**相等** | 指错环境的表现是「功能坏了但没有任何报错」，最难查的一类 |

## ⚠️ 这个 Skill 自己被修过 9 处（2026-10-11，全部是误报、漏报和一处自己引入的回归）

**第一次跑出 17/24，7 个 FAIL。我逐个查证后，一个真 bug 都没有，全是检查项本身写错了。**
下面每一条都是当时的具体错法，因为它们**还会再犯**。

### 一、没剥注释 → 把「我们特意避开了 X」判成违规（3 处误报）

`schema.sql` 的注释里写着「用 SMALLINT **不用 BOOLEAN / TINYINT(1)**」，
三个云函数的注释里写着「为什么**不用**通配符 `'*'`」。
A1 和 B4 直接匹配到了这些**说明文字**。

→ 现在 A1 走 `strip_sql_comments()`，B4 走 `strip_js_comments()`。
**写任何基于文本模式的检查，第一件事是剥注释。**

### 二、查窄了一层 → 找错了文件（1 处误报）

B3 查 `index.js` 里的 `CLOUDBASE_*`，但**真正读环境变量的代码在 `*Repository.js` 里**。
`index.js` 里出现的全是注释里的部署说明。

→ 教训：检查项要问「这段逻辑**在哪**」，别假设在「看起来最像」的文件里。

### 三、只支持一种合法写法 → 另一种被误判（3 处误报）

`items`/`anniversaries` 用 `var ALLOWED = ['GET','POST',...]` 数组声明方法，
检查项却只认 `if (method === 'POST')` 这种逐个 if 的写法 → 全判成「缺 GET」。

更严重的是：`reminders` 是**设计上只读**（Day 19 的函数，只有 `list`，
没有 insert/update/remove）。检查项对它要求四方法，等于**要求一个不存在的功能**。

→ 现在 B5 两种写法都认，且先看 Repository 有没有 insert 来判定这个函数到底是不是写函数。
B7/B8 同理，改成只对「实现了 remove / insert」的函数提要求。

### 四、把「抽取真源码执行」当成了「手写桩」（10 处误报）

C4 报 10 个桩没跟上。实际上本项目**多数测试是从 `index.html` 抽取真源码执行**
（正确做法，桩就是源码本身，永远不会漏），只有 `test_day24_bug_fixed.js` 才手写桩。

→ 现在只对含 `var syncJobs = {` 的测试查桩。

### 五、正则匹配不到 → 整条检查静默失效（漏报，最险的一种）

A5 的写入端校验用了 `\n  \}` 收尾，但 `toDbItem` 的函数体实际以 `\n    }` 结尾。
**正则一个函数都没匹配到**，而报告里「没匹配到」和「匹配到且没问题」长得一模一样。

→ 现在 A5 的证据里直接写出「校验了几个函数」，`n_fn >= 2` 不满足就 FAIL。
**任何依赖正则的检查，证据里必须带上「匹配到了多少个对象」**，否则你分不清
「没问题」和「根本没查到」。

### 六、判据松到没有意义（漏报）

E3 第一版写的是「前端有 env **且** 云函数文件里有 `habit-checkin-` 字样」。
把前端换成 `wrong-env-000` 后，云函数 README 里的 `habit-checkin-` 照样命中 → PASS。

→ 现在改成**两边的 env id 必须相等**。

### 七、注入破坏的脚本自己失败，还差点当成「检查有漏报」

第一轮注入破坏时，我用的锚点跟文件里的真实写法不一致（列名后面是对齐用的多个空格），
**两处破坏根本没落盘**。跑出来「没抓到」，我一度以为是检查项漏报。

→ 注入后**必须 grep 确认落盘**（脚本每次都打印 `ok:` / `!! 锚点未命中`，
并且我另外跑一次 grep 数命中次数）。
这跟项目记忆里那条「脚本报缺失时先用 grep 查原文再信」是同一个坑。

### 八、检查脚本自己崩了会伪装成通过

第一版输出时**明细全没了，只剩「17/24 通过」**：`check()` 里 gate 标记是 `A1`/`B2`，
输出时却按 `A`/`B` 精确匹配 → 明细被全部过滤掉。

→ 现在用 `startswith` 匹配，且每组 `gate()` 外面包了 try/except，
整组崩了会记成「（X 整组执行出错）」FAIL —— **检查脚本自己的失败不能算通过**。

### 九、「改进」正则时改出了回归（2026-10-11 最隐蔽的一次）

修完上面几条后重跑，出现一个**新的** FAIL：`前端 None，但云函数里是 habit-checkin-…`。

真因：修 E3 时我顺手把正则从 `[a-z0-9\-]+-` 改成**非贪婪**的 `[a-z0-9\-]+?-\d+-`，
想着「更精确地只吃 env id」。但 env id 自身含非数字字符
（`habit-checkin-d9giln6ke6594e88b`），后面跟的是 `-1499597872.`，
**`-\d+-` 永远匹配不上** → `front_eid` 恒为 None → 判据崩了。

更糟的是它**报错信息误导人**：输出「指错环境了」，会让人去查配置文件，
而真因是检查脚本自己的正则挂了。

→两条修正：
1. 正则改成 `[a-z0-9][a-z0-9\-]*?)-[0-9]+\.`，在真实 URL 上验证过才落盘；
2. E3 现在把「URL 解析失败」和「env 真的不一致」**分开报**，
   并且修复后又反向注入 `wrong-env` 验证过仍能抓到 —— **改完必须回归验证，没削弱检测力**。

→ 教训：**修复误报时引入的回归，比原来的误报更贵**，因为它会让你怀疑代码而不是怀疑检查项。
改完正则先在真实样本上 `re.search` 试一次，再跑全量。

## 新增检查项时必须做的三件事

1. **写出它的出处**（哪个 bug、哪次事故），放进 `why` 参数 —— 没出处的规则会被删掉
2. **故意弄坏一次，确认它真的 FAIL** —— 没被破坏验证过的检查项等于没写
3. **确认剥注释/匹配范围没有把真代码排除掉** —— 拿证据里的「匹配到几个对象」对一下，
   数量不对就是静默失效

## 维护

改检查项时同步改本文件的表格和「被修过 9 次」那一节 ——
**这节是本 Skill 最有价值的部分**，它记录的是「哪些写法会骗过检查」，
比检查项本身更容易忘。
