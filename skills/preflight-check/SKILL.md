# 发布前检查（preflight-check）

## 何时触发

- **任何**「发布 / 上线 / 同步线上 / 部署」动作**之前**，必跑一次
- 改过 `index.html` / `sw.js` / `manifest.json` / `assets/` 里任何东西之后
- 用户反馈「线上还是旧的」「图裂了」「点了没反应」时（先跑一次，看是不是发布环节漏了什么）

**不触发**：只改文档（`.md`）、只改记忆文件、只改云函数代码（不涉及页面发布）时不用跑。

## 怎么跑

```bash
python preflight.py --online          # 完整版（发布前 / 发布后各跑一次）
python preflight.py                   # 只跑本地部分（拷完文件、发布之前）
python preflight.py --online https://你的域名
```

退出码 `0` = 全通过，`1` = 有失败项。**没全绿之前不要发布。**

理由：发布是**覆盖式**的 —— 线上链接可能已经分享给别人，覆写之后没法撤回。

## 六道闸，每道都有一句话理由

脚本会自动跑完并输出 PASS/FAIL。这里写清每道**在拦什么**，
这样看到 FAIL 时知道该修什么，而不是只知道「检查没过」。

### A1 · JS 语法

**拦什么**：`index.html` 是单文件 3000+ 行的内联 JS，一个多余的花括号**不会**让浏览器指出位置。
页面只是某块功能静默不响应（「点了没反应」是本地最难查的一类）。
`sw.js` 是独立文件，一并查 —— 2026-10-10 线上 `sw.js` 404 时没有任何报错。

### A2 · id 空引用

**拦什么**：**最高频的静默失败**。
`getElementById` 返回 null 后紧跟 `.addEventListener` 会抛 TypeError；
如果那个绑定在初始化里，**后面的初始化代码全不执行**——
表现是「某个按钮全都点了没反应」。

### A3 · 资源引用完整性 + 大小写

**拦什么**：两件事。
① 引用了不存在的文件；
② **大小写不匹配** —— Windows/macOS 文件系统不区分大小写，**Linux 区分**。
`Logo.png` 写进 HTML，本地能显示，传上去就 404。**本地永远测不出来。**

### B1 · 发布目录一致性

**拦什么**：本项目是**手动拷文件**，所以最容易漏。
逐个确认 `index.html` / `sw.js` / `manifest.json` 都在 `.deploy/` 里，
且**内容跟仓库根是同一份**（B1b 比哈希）—— 「文件在但还是旧版」比「文件不在」更隐蔽。

> ⚠️ **发布目录是 `.deploy/`，不是仓库根目录**（避免文档被公网读到）。

### B2 · assets 同步（含 png）

**拦什么**：**必须同时拷 `*.jpg` 和 `*.png`**。
png 是看板娘透明立绘，jpg 存不了 alpha。沿用「只拷 *.jpg」的老命令，线上就裂图。

### B3 · 密钥泄露

**拦什么**：`.deploy/` 是公网可读的。服务端 API Key 进了前端代码就等于公开。
脚本查 `eyJ...` 形态的 JWT 和 API Key 赋值。

### C · 线上验证（要 `--online`）

**拦什么**：三个只有发布完才知道的事。
① **precache 清单每项真的取得到** —— SW 最隐蔽的坑：
   precache 里**只要有一条 404，`cache.addAll()` 就整体 reject，SW 安装直接失败，
   整个离线能力静默失效**，控制台只留一条 warn。
② 关键文件在线可达；
③ **线上是不是新版**（grep 本地的 API 路径当特征串）；
④ 图片在线全可达（**裂图不会报错，只能这么拦**）。

## ⚠️ 三条读 curl 输出时栽过的坑（都是实测，不是听说的）

### 一、`%{http_code}` 是可靠的，但 `curl -I` 的输出要**读最后一行**

2026-10-11 我一度断定「这个环境里 `%{http_code}` 对不存在的文件返回 200，
必须改用 `curl -sf`」—— **这个结论是错的**，已实测推翻：

```text
curl -s -o /dev/null -w "%{http_code}" 不存在的文件   → 404    ✅ 可靠
curl -sf -o /dev/null -w "%{http_code}" 同上         → 404, 退出码 22  ✅ 也对
```

**真正的坑在于我用错了命令**：当时打的是 `curl -sI`（只看响应头，不发 body），
它的输出是这个环境特有的两段式：

```text
HTTP/1.1 200 Connection Established      ← 代理的 CONNECT 隧道协商行，不是资源状态
HTTP/1.1 404 Not Found                   ← 这才是资源状态，在最后一行
```

我 grep 了 `HTTP/` 模式，**读到第一行就下结论**，于是「404」被我看成了「200」。

→ **教训（比命令本身重要）**：判状态码要用 `curl -s -o /dev/null -w "%{http_code}"`
这种**只吐一个数字**的形式，别去读两段式的原始头。
→ 两个命令都保留在脚本里：`rc != 0` 走 `-sf` 的退出码（防代理返回非 2xx 但 body 是错误页）。

⚠️ 这也说明**我自己的结论需要复核**。写下「某工具不可靠」之前，
先用**两种方法**各测一遍真实存在和不存在两种输入 —— 只测一种就会得出错的规则。

### 二、SW 缓存的是「sw.js 自己的字节」

**改了 `index.html` 但没改 `sw.js`，浏览器认为 SW 没更新，用户永远拿旧版。**

所以 `sw.js` 里那个 `VERSION` 常量**必须随每次发布变化**，保证字节变。
本项目现在是 `const VERSION = 'day24-v1'` —— **每次发布都要手动改它**。

`sw.js` 本身也绝不能长缓存（`max-age` 越长更新越慢）。当前线上没有 `Cache-Control` 头，
靠 `Eo-Cache-Status: MISS` 兜着（每次回源），能用，但改 SW 时要记得这个前提。

## 完整发布流程（含这个检查的位置）

```bash
# 1. 改完代码，先跑本地检查
python preflight.py                    # 此刻 B1b 会 FAIL（还没拷）—— 正常

# 2. 拷进发布目录
cp index.html .deploy/
cp sw.js .deploy/                      # ⚠️ 2026-10-10 漏过这条
cp manifest.json .deploy/
cp assets/*.jpg assets/*.png .deploy/assets/   # ⚠️ png 也要拷

# 3. 再跑一次 —— 这次该全绿
python preflight.py

# 4. 发布

# 5. 发布后验线上
python preflight.py --online

# 6. 手动把 sw.js 的 VERSION 改掉（见上面「坑二」）
```

⚠️ **发布不自动同步** —— 改完功能必须手动重新发一次，否则线上还是旧版。
